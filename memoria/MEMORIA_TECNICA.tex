\section*{0. Resumen ejecutivo}
\addcontentsline{toc}{section}{0. Resumen ejecutivo}

El Ayuntamiento de Albacete licita una solución de \textbf{smart parking} que monitorice en tiempo real las plazas del entorno universitario (BBOX \texttt{38.976059, -1.858728 $\rightarrow$ 38.983215, -1.846111}, $\approx$ 0,55 km$^2$) y exponga la disponibilidad a apps de movilidad, vehículos autónomos (vía C-V2X) y paneles informativos. TECO S.L.\ (rol del autor) responde con una arquitectura end-to-end en cuatro capas: (1) sensórica magnética AMR por plaza más cámaras ANPR puntuales en accesos; (2) conectividad NB-IoT como red principal y LoRaWAN/5G como complementos; (3) plataforma cloud AWS serverless (IoT Core + Lambda + DynamoDB + API Gateway); (4) aplicaciones API REST OpenAPI 3.0 (salida GeoJSON) y dashboard Streamlit.

El prototipo cubre el flujo extremo a extremo con 40 plazas simuladas en 4 sub-zonas reales (Z1-CAMPUS, Z2-DEPORTIVO, Z3-SANITARIO, Z4-RESIDENCIAL), desplegado en AWS Academy Learner Lab con scripts boto3 idempotentes. La latencia medida sensor$\rightarrow$API es \textbf{$<$ 2 s}, el coste cloud del piloto \textbf{$<$ 5 USD/mes} y la arquitectura escala linealmente a 10\,000 plazas con coste cloud aproximado de \textbf{6 céntimos/plaza/mes}.

\section{Descripción del problema y entorno}

\subsection{Contexto}
Entre el 15\,\% y el 30\,\% del tráfico urbano (Shoup, 2005) lo generan vehículos buscando aparcamiento, con impacto directo en tiempo, emisiones y confort. Albacete ($\approx$ 175\,000 hab.) propone como piloto el corredor entre Campus UCLM, Estadio Carlos Belmonte, Hospital Universitario y la zona residencial sur de la AB-20, alineado con el Pacto Verde Europeo y la llegada de la movilidad autónoma.

\subsection{Decisión razonada}
Se adopta una \textbf{arquitectura híbrida}:
\begin{itemize}
\item \textbf{Sensor principal: AMR magnético bajo asfalto, uno por plaza.} Sellado IP68, calibración in situ, debounce 2-3 s, vida 5-7 años, $\approx$ 75 €/ud. Gana en consumo y coste a ultrasónico, radar y LIDAR, y en privacidad y simplicidad a la cámara.
\item \textbf{Complementario: 6-8 cámaras ANPR puntuales} en accesos (N-430, C.\ San Juan, C.\ Imperial, Av.\ de la Mancha) para conteo agregado y futuro control de zonas de bajas emisiones; nunca para detección plaza a plaza (mitiga el riesgo RGPD).
\item \textbf{Sensores ambientales} (NO$_2$, PM2.5, CO$_2$, ruido) 1 cada $\sim$150 plazas como analítica complementaria.
\end{itemize}

\subsection{Modelo del nodo y payload}
Cada plaza es un \texttt{Thing} en AWS IoT Core con atributos \texttt{spotId, zoneId, street, lat, lon}. Payload MQTT (topic \texttt{parking/\{zoneId\}/spot/\{spotId\}/status}):

\begin{lstlisting}
{
  "spotId": "ALB-Z1-001", "zoneId": "Z1-CAMPUS", "street": "C. Imperial",
  "lat": 38.97765, "lon": -1.85745, "status": "occupied",
  "batteryLevel": 92.2, "confidence": 0.94,
  "sensorType": "magnetic", "timestamp": 1778929200072
}
\end{lstlisting}

Política de envío: cambio de estado inmediato tras debounce, heartbeat cada 5 min, auto-test diario, alarma de manipulación y aviso de batería baja ($<$ 20\,\%).

\subsection{Calibración, instalación y mantenimiento}
Calibración inicial en taller (linealización del magnetómetro) y final \emph{in situ} (medida del campo terrestre sin vehículo), 5-10 min/ud. Instalación nocturna por cuadrillas de 2 operarios con maquinaria menor, rendimiento típico 30-40 plazas/noche. Mantenimiento: revisión por muestreo cada 6 meses; sustitución de pila prevista a los 5 años; firmware actualizable OTA vía LPWAN cuando la pila lo permite o por visita técnica programada.

\subsection{Plan de despliegue}
\textbf{Fase 0 (semanas 1-4):} mapa exacto de las $\approx$ 500 plazas con coordenadas y prioridades, coordinación con Movilidad y EMT para cortes nocturnos, acuerdo con operador NB-IoT (tarifa SIM M2M, APN privado) y acuerdo con el responsable de la red WAN municipal. \textbf{Fase 1 (semanas 5-10):} 3 gateways edge sobre farolas o mobiliario urbano alimentados por alumbrado público, 20 sensores piloto en Z1-CAMPUS, despliegue del backend AWS y 2-3 semanas de validación operativa. \textbf{Fase 2 (semanas 11-20):} instalación nocturna de los $\approx$ 500 sensores restantes ($\sim$35/noche), 6-8 cámaras ANPR en accesos, 4 nodos ambientales, onboarding masivo con IoT Provisioning Templates. \textbf{Fase 3 (mes 6-12):} KPIs de servicio (uptime, latencia E2E, tasa de falsos positivos), iteración del agregador, integración con paneles DMS municipales. \textbf{Fase 4 (año 2):} escalado por barrios e integración C-V2X (RSU/MEC).

\subsection{Estimación de tráfico (piloto)}
500 plazas $\times$ 5 cambios/día = 2\,500 eventos; 500 $\times$ 288 heartbeats/día = 144\,000; total $\approx$ \textbf{150\,000 mensajes/día ($\sim$85 MB)}. Pico evento deportivo: hasta 1\,000 cambios/min durante 15 min. Asumible por NB-IoT y por la capa cloud (cap.\ 8).

\subsection{Diagrama de arquitectura}
\begin{lstlisting}
Sensor AMR --MQTT/TLS--> AWS IoT Core --> IoT Rule (SQL) --> Lambda ingest
                                                              |
                                                              +-> DynamoDB parking-state
                                                              +- async --> Lambda aggregator
                                                                              |
                                                                              +-> DynamoDB zone-kpis
                                                                                          |
Dashboard / Vehiculo / App <--HTTPS-- API Gateway <-- Lambda api <----------+
\end{lstlisting}

\subsection{Flujo extremo a extremo}
\begin{enumerate}
\item Sensor publica MQTT/TLS sobre \texttt{parking/\{zoneId\}/spot/\{spotId\}/status}.
\item IoT Core autentica vía mTLS X.509 y entrega al broker.
\item La IoT Rule (\texttt{SELECT * FROM 'parking/+/spot/+/status'}) dispara la Lambda ingest.
\item La Lambda ingest hace UPSERT en \texttt{parking-state} y, si cambia el estado, invoca de forma asíncrona la Lambda agregador con el \texttt{zoneId}.
\item La Lambda agregador hace \texttt{Scan} filtrado por zona, calcula libres/ocupadas/ratio y escribe una fila en \texttt{zone-kpis} con \texttt{windowEnd}.
\item API Gateway expone \texttt{/spots}, \texttt{/spots/\{id\}}, \texttt{/zones}, \texttt{/zones/\{id\}/kpis} y los integra con la Lambda api (JSON o GeoJSON).
\item Cliente (dashboard o tercero) consume por HTTPS; CloudWatch recoge logs.
\end{enumerate}

\subsection{Modelado de Things y policy}
Todos los sensores pertenecen al \texttt{Thing Type} \texttt{smart-parking-albacete-sensor-type} y al \texttt{Thing Group} \texttt{smart-parking-albacete-fleet} (facilita acciones masivas). En el piloto comparten un único certificado y la policy \texttt{smart-parking-albacete-sensor-policy}, que autoriza solo \texttt{Connect/Publish/Subscribe/Receive} sobre topics \texttt{parking/*}. En producción se generaría un certificado por dispositivo (Fleet Provisioning Templates) para revocaciones granulares.

\subsection{Reparto edge / cloud}
\textbf{Edge (diseño con IoT Greengrass v2):} filtrado de ruido del magnetómetro, debounce y detección de cambios reales, caché de hasta 24 h ante caída de conectividad, agregación simple por zona, procesamiento ANPR local con envío de solo metadatos (hash, dirección, recuento). \textbf{Cloud (implementado):} normalización del payload, persistencia de estado y agregados, APIs internas y externas, seguridad, observabilidad.

\subsection{Nota sobre interoperabilidad (FIWARE, opcional)}
El enunciado exige AWS y contempla la posibilidad de proponer una integración híbrida con \textbf{FIWARE} si se justifica. Esta línea es relevante en el contexto europeo porque numerosos pliegos municipales (Open \& Agile Smart Cities, proyectos H2020/Horizon Europe) demandan compatibilidad con el modelo NGSI-v2 / NGSI-LD y con los Smart Data Models públicos del catálogo \texttt{smart-data-models.github.io} (\texttt{ParkingSpot}, \texttt{ParkingZone}, \texttt{ParkingSensor}). Para fases posteriores se prevé exponer un endpoint adicional alimentado por la misma Lambda de ingesta (con un \texttt{POST} al Context Broker Orion tras escribir en DynamoDB), de modo que un tercero pueda consumir por NGSI-v2 sin tocar el resto de la arquitectura. En el piloto \textbf{no se despliega} Orion porque añade contenedores y puntos de fallo que no aportan valor académico extra dado el límite de 3 h del lab, y porque el contrato REST + GeoJSON ya cubre los requisitos funcionales exigidos.

\section{Modelo de datos y APIs}

\subsection{Modelado físico en DynamoDB}
\textbf{Tabla \texttt{*-state}} (estado actual, PK \texttt{spotId}): \texttt{zoneId, street, lat, lon, status} (free/occupied/unknown), \texttt{batteryLevel, confidence, sensorType, lastUpdated}. Modo PAY\_PER\_REQUEST. Operaciones principales: \texttt{PutItem} (UPSERT) desde la Lambda ingest y \texttt{Scan} filtrado por \texttt{zoneId} desde la Lambda agregador y la Lambda api. En escenario ciudad: GSI \texttt{zoneId-status-index} para sustituir el \texttt{Scan} por \texttt{Query}.

\textbf{Tabla \texttt{*-zone-kpis}} (serie temporal, PK \texttt{zoneId}, SK \texttt{windowEnd} ISO 8601): \texttt{totalSpots, freeSpots, occupiedSpots, unknownSpots, occupancyRate, computedAtMs}. Permite consultas naturales del tipo \emph{últimos N KPIs de Z1}.

\subsection{APIs internas vs externas e idempotencia}
La API pública es de solo lectura, con rate-limit y opcional API key/Cognito. La API interna (operador) permite forzar \texttt{unknown} para plazas en obras y queda protegida con IAM y red privada (documentada, no desplegada). La Lambda ingest hace \texttt{PutItem} idempotente; en escenarios con orden estricto se introduce \texttt{ConditionExpression: lastUpdated < :ts}. El versionado se hará en el path (\texttt{/v1/}, \texttt{/v2/}) al pasar a productivo.

\section{Seguridad y privacidad}

\subsection{Modelo de amenazas (resumen)}
\begin{longtable}{p{3.5cm}p{4.5cm}p{6.5cm}}
\toprule
\textbf{Activo} & \textbf{Amenaza} & \textbf{Mitigación} \\ \midrule
\endhead
Sensor físico & Manipulación, robo & Caja blindada, alarma de movimiento \\
Identidad sensor & Suplantación & Certif.\ por dispositivo + rotación + revocación \\

\end{longtable}

\subsection{Implementación}
\textbf{Dispositivo:} un \texttt{Thing} por plaza con certificado X.509 compartido en el piloto y policy restrictiva (\texttt{Connect/Publish/Subscribe/Receive} sobre \texttt{parking/*}). En producción: un certificado por dispositivo (Fleet Provisioning), renovación 12-24 m y AWS IoT Device Defender.

\textbf{Transporte:} TLS 1.2 obligatorio (puerto 8883), mTLS con CA AWS IoT, validación de \texttt{AmazonRootCA1.pem} en el dispositivo. API REST siempre por HTTPS.

\textbf{Procesamiento:} las tres Lambdas corren bajo \texttt{LabRole} (limitación del lab); en producción se sustituiría por un rol IAM por Lambda con políticas a medida (\texttt{ingest} solo \texttt{PutItem} sobre \texttt{*-state}, \texttt{aggregator} \texttt{Scan/PutItem}, \texttt{api} solo lectura). Sin credenciales en claro.

\textbf{Persistencia:} DynamoDB cifrado en reposo con KMS gestionado por AWS; en producción CMK propia. Point-in-Time Recovery con 35 días de retención.

\textbf{Exposición:} HTTPS + CORS controlado. Diseñado para producción: API Keys + Usage Plans (10\,000 req/día por app), Cognito o JWT custom, AWS WAF y custom domain con ACM.

\textbf{Operación:} CloudWatch Logs + CloudTrail (audita toda la API AWS) + AWS Config (alerta de cambios en IAM o certificados).

\subsection{Cumplimiento RGPD (privacy by design)}
No se almacenan datos personales. Las cámaras ANPR procesan la matrícula \textbf{localmente en el gateway} y solo envían a la cloud un hash unidireccional y la dirección de paso; las imágenes originales se retienen un máximo de 72 h localmente. Las consultas a la API son anónimas. Retención: KPIs agregados 24 meses; logs operacionales a S3 Glacier tras 90 días.

\subsection{Plan de respuesta a incidentes}
\begin{enumerate}
\item \textbf{Detección:} alertas de CloudWatch o IoT Device Defender (intentos de conexión rechazados, picos de tráfico anómalos).
\item \textbf{Contención:} revocación inmediata del certificado afectado (\texttt{iot:UpdateCertificate} a \texttt{REVOKED}).
\item \textbf{Erradicación:} rotación de certificados afectados y sustitución física del sensor si hay sospecha de manipulación.
\item \textbf{Recuperación:} restauración del estado desde DynamoDB PITR si fue manipulado.
\item \textbf{Post-mortem:} revisión de logs CloudTrail y CloudWatch, informe a la concejalía y mejora de la policy o la lógica afectada.
\end{enumerate}

\section{Escalabilidad: del piloto a la ciudad}

\subsection{Conclusiones del análisis de coste}
\begin{enumerate}
\item La fracción cloud del coste es marginal frente al hardware y la operación física.
\item El coste cloud crece aproximadamente lineal con el número de plazas; el verdadero motor del TCO es la flota física.
\item NB-IoT como red elegida es decisiva en el OPEX: cualquier alternativa con cuota mensual $>$ 2 €/SIM duplicaría el coste operativo.
\item La arquitectura serverless evita inversión en infraestructura cloud propia (sin EC2/RDS) y permite un piloto encuadrable en el presupuesto típico de un proyecto de innovación de un ayuntamiento mediano.
\end{enumerate}

\subsection{Defensa: preguntas previsibles}
\begin{itemize}
\item \textbf{¿Por qué AMR magnético?} Privacidad, consumo (5-7 años), coste ($\sim$75 €), robustez IP68; cámaras solo en accesos como conteo agregado.
\item \textbf{¿Y si falla un sensor o gateway?} Sensor: heartbeat ausente detectado por auditoría \texttt{lastUpdated} (futura alerta SNS). Gateway: redundancia por zona. Conectividad: buffer local y reenvío.
\item \textbf{¿Cómo evitar falsos libres/ocupados?} Debounce 2-3 s en edge, umbral \texttt{confidence}, calibración in situ, filtrado en la Lambda.
\item \textbf{¿Cómo se escala a 10\,000 plazas?} Kinesis como buffer, GSI en DynamoDB, WAF + CloudFront; coste cloud $\approx$ 440 €/mes.
\item \textbf{¿Qué latencia se espera?} NB-IoT 1-3 s + IoT/Lambda/DDB 50-300 ms + API 100-500 ms; total $<$ 5 s (medido 2-3 s).
\item \textbf{¿Estado vs histórico?} \texttt{parking-state} sobrescribe; \texttt{zone-kpis} indexa por \texttt{(zoneId, windowEnd)}; raw events a S3 (diseño).
\item \textbf{¿Cómo proteges la API?} HTTPS, CORS, throttling y API keys, WAF y Cognito (producción), IAM mínimo privilegio.
\item \textbf{¿Qué es real y qué simulado?} Real: AWS IoT Core, 3 Lambdas, 2 DynamoDB, API GW, dashboard. Simulado: sensores físicos (paho-mqtt sobre MQTT/TLS real), cámaras ANPR, gateway edge.
\item \textbf{¿Por qué AWS y no FIWARE?} El enunciado exige AWS. FIWARE se contempla como posible capa de interoperabilidad opcional (cap.\ 5.7), no como sustituto.
\end{itemize}
